# **FactorStore：高性能量化因子存储引擎**

这份文档记录最初的设计设想。当前实现见[设计文档](design.md)和[接口文档](api.md)。

## **一、项目定位**

FactorStore 是一个基于 C++17 实现的轻量级量化因子存储引擎，主要面向量化交易、因子研究和历史回测场景，为因子数据提供高效的批量写入、批量查询和数据管理能力。

项目采用嵌入式存储库的形式，不依赖 MySQL、Redis 等外部服务，调用方可以直接通过 C++ 接口进行数据操作。

核心设计目标是：

- 高性能：提高大规模因子数据的批量读写效率。
- 低内存开销：减少重复存储和无效空间占用。
- 并发安全：支持多线程同时读写因子数据。
- 数据持久化：支持磁盘存储与数据恢复。
- 可扩展性：支持因子、合约和历史日期的动态增长。

## **二、整体架构**

整个项目主要分为统一接口层、元数据与索引层、核心存储引擎、持久化管理层四个业务层次，底层使用磁盘文件保存数据。

## **三、核心数据存储设计**

### **1. 因子优先的分块存储**

因子数据具有三个维度：因子、合约、交易日期。

我打算采用因子优先的存储结构，并按照合约和年份进一步划分数据块。

**FactorStore**

**Factor 0（momentum）**

IF2606 · 2026

IC2606 · 2026

IH2606 · 2026

**Factor 1（volatility）**

IF2606 · 2026

IC2606 · 2026

IH2606 · 2026

每个 YearBlock 独立保存某个因子、某个合约在某一年的全部数据。

这种设计可以方便地进行年度批量写入、历史数据查询和整个因子的删除，同时避免全局数组扩容时复制大量数据。

### **2. 整数编码与组合索引**

将因子名称和合约名称映射为整数 ID，避免在底层存储中重复保存和计算字符串。

使用 FactorID 直接定位因子对象，并将 ContractID 与 Year 组合成一个 64 位整数，作为数据块的索引。

```
uint64_t key = (uint64_t(contractId) << 32) | year;
```

最终的数据定位过程为：

```
FactorID
    ↓
64 位组合 Key
    ↓
YearBlock
    ↓
年内日期下标
    ↓
double
```

这样可以减少多级哈希查找和重复索引开销。

### **3. 自适应稀疏与稠密存储**

每个 YearBlock 支持两种存储模式。

| 存储方式 | 实现方式               | 适用场景   |
| ---- | ------------------ | ------ |
| 稀疏存储 | 有序日期数组 + 数值数组      | 有效数据较少 |
| 稠密存储 | double 数组 + Bitmap | 有效数据较多 |

数据块初始采用稀疏存储，当有效数据数量达到一定阈值后，自动转换为稠密存储。

通过这种方式，在降低内存占用的同时，保证高密度数据的访问效率。

## **四、批量读写优化**

| 题目要求 | 接口 | 做法 |
| --- | --- | --- |
| 批量插入某个合约某一年的某个因子 | `upsert_year` | 找到一个年度块，一次写入多天 |
| 批量插入某天一批合约的一批因子 | `upsert_day` | 按因子和合约写入当天的值 |
| 查询当前总共有多少个因子 | `factor_count` | 直接取目录长度 |
| 删除某个因子 | `erase_factor` | 移除该因子及其所有数据 |
| 根据合约列表、日期列表和因子列表查询数据 | `query` | 按年整理日期，同一块只需找一次 |

查询结果使用连续的 double 数组和有效位图进行存储，减少结果集的内存占用，并区分缺失数据与合法的零值、NaN 值。

## **五、并发控制设计**

采用全局元数据读写锁与因子级读写锁相结合的方式。

全局锁负责保护 ID 映射、因子目录和因子数量，因子级锁负责保护单个因子内部的数据。

这样可以实现：

- 多个线程同时查询同一个因子。
- 多个线程同时写入不同因子。
- 同一个因子的读写操作正确互斥。
- 在访问因子期间持有目录锁，删除时独占目录，确保因子对象在使用期间有效。
- 通过统一的加锁顺序避免循环等待。

后续如果发现同一个因子内部存在较大的锁竞争，可以进一步引入分片锁。

## **六、持久化存储设计**

持久化作为独立的增强模块进行开发。

采用自定义二进制文件格式，按照因子和年份组织磁盘数据。

```
data/
├── catalog.bin
├── factors/
│   ├── factor_0/
│   │   ├── 2025.bin
│   │   └── 2026.bin
│   └── factor_1/
│       └── 2026.bin
└── wal/
    └── active.wal
```

在基础文件存储实现完成后，根据实际需求逐步引入：

| 技术              | 作用           |
| --------------- | ------------ |
| 磁盘偏移索引          | 快速定位磁盘数据块    |
| LRU Block Cache | 缓存热点数据块      |
| WAL             | 支持崩溃恢复       |
| Checkpoint      | 持久化状态与回收日志   |
| Compaction      | 回收旧版本数据占用的空间 |
| mmap            | 可选的文件读取优化    |

## **九、项目核心技术亮点**

最终这个项目应该重点体现以下六个技术亮点：

1. **分块存储机制**：针对因子数据的三维特征设计因子优先、合约年份分块的存储结构。
2. **自适应存储机制**：根据数据密度动态选择稀疏或稠密存储，平衡空间与性能。
3. **高效索引机制**：通过整数编码、直接索引和组合 Key 减少重复哈希计算。
4. **批量访问优化**：通过 ID 预解析、数据分组和索引复用提高批量读写效率。
5. **细粒度并发控制**：通过因子级读写锁实现不同因子之间的并行访问。
6. **可扩展持久化机制**：通过独立的持久化模块支持磁盘存储和后续崩溃恢复能力。

## **十、项目实现原则**

我打算将 FactorStore 做成一个**针对量化因子访问特点进行专项优化的 C++ 嵌入式存储引擎，而不是一个通用数据库。**

首先完成正确、可用、高效的内存存储版本，然后通过性能测试证明各项优化的实际价值，最后逐步增强并发和持久化能力。

原题并没有强制要求并发、持久化和事务机制，因此这些属于我们主动增加的工程设计。当前也没有实际性能测试结果，最终应根据测试数据决定保留哪些优化，避免为了增加技术亮点而过度设计。
